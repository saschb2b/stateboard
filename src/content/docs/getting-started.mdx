---
title: Getting started
description: Create a product board, start a release assessment, or use the visual screenshot workflow.
---

Start by creating a product board. The current development build opens its readiness workspace, where capabilities connect outcomes, dependencies, and verification. The readiness MVP is unreleased; the latest published `2026.8.0` release supports the existing visual workflow.

Use the [release readiness guide](/docs/release-readiness) for an assessment from candidate selection through evidence, decision, and curated sharing. The steps below also show how to add visual anchors and share a visual board.

## 1. Run StateBoard

For a local spin-up, the repo ships a `docker-compose.yaml` with Postgres and a pre-seeded Keycloak (test users `alice` / `bob`, password = username):

```bash
cp .env.example .env
docker compose up -d        # Postgres + Keycloak
pnpm install
pnpm migrate                # create the tables
pnpm dev
```

Open [http://localhost:3000](http://localhost:3000) and click **Open workspace**. You'll be sent to sign in: choose **Continue with Keycloak** and log in as `alice` — the first sign-in becomes the workspace owner.

For a real deployment (your own Keycloak, via Docker Compose or Helm), see [Self-hosting](/docs/self-hosting).

<Callout type="info">
  Boards and regions live in Postgres; uploaded screenshots live on a filesystem
  volume (`./data/` from source, or the mounted volume in production). Back up
  both together, including the private `release-assets/` directory used by
  recorded decisions.
</Callout>

## 2. Create a board

On `/boards`, click **New board**. Give it a name, usually a product or a quarter, e.g. `Acme Dashboard / Q2`. The description is optional.

The development build opens **Release assessments** after creation. Add capabilities and follow the [release workflow](/docs/release-readiness), or choose **Screens** to open the visual editor. Existing boards need no conversion.

Already have a visual board that's close to what you need? Click **Duplicate** on its card to deep-copy every screen and region into a new board, then swap only the screens that changed — faster than starting over.

Each board has an internal ID used in its workspace URLs. Public visual links use revocable tokens at `/share/{token}`; curated release links use separate tokens at `/share/releases/{token}`. Keep internal assessment URLs for workspace members and publish the public summary deliberately.

## 3. Upload a screen

Choose **Screens** in the product workspace, then drop a screenshot onto the upload area or click to browse. Allowed formats: PNG, JPEG, WebP, GIF. Max 25 MB per file.

You can upload as many screens as you want. They appear in the screen sidebar. Use its screen actions to reorder them; the order carries through to the share view and Present mode.

<Callout type="warn">
  Don't upload anything you can't show stakeholders. Share links are public by
  design — anyone with the link can see every screen on that board, no login.
</Callout>

## 4. Mark your first region

With a screen open, **click and drag** anywhere on the image to draw a rectangle. When you release, a side panel slides in. Pick a state, give the region a label, optionally add notes.

Three states only, by design:

- **Shipped** · live, real data, fully wired up.
- **Mock** · UI is in place but data is hardcoded or fake.
- **Missing** · not built yet.

Press **Esc** at any time to discard a draft region.

## 5. Share it

Click **Share** in the header to copy the read-only URL. The arrow beside it opens a menu with **Open share view** (the public page in a new tab) and **Manage links** (mint extra links or revoke one).

This visual link shows every screen and region on the board. A release review needs capabilities and verification too; publish a [curated recorded decision](/docs/release-readiness#record-and-share-a-decision) when sharing release readiness.
