Start by creating a product board. The current development build opens its readiness workspace, where features describe what should work and checks record what was observed. The readiness MVP is unreleased; the latest published `2026.8.0` release supports the existing visual workflow.

Use the [release readiness guide](/docs/release-readiness) to review a candidate, record check results, and make a release decision. AI, screenshots, and architecture records are optional. The steps below also show how to add visual anchors and share a visual board.

Use the language button in the header to choose **English** or **Deutsch**. The development build saves this preference in your browser. Switching language preserves open forms and the current view. Names, evidence, and other entered content keep their original language; these guides and API diagnostics remain in English.

## 1. Run StateBoard

For a local spin-up, the repo ships a `docker-compose.yaml` with Postgres and a pre-seeded Keycloak (test users `alice` / `bob`, password = username):

```bash
cp .env.example .env
docker compose up -d        # Postgres + Keycloak
pnpm install
pnpm migrate                # create the tables
pnpm dev
```

Open [http://localhost:3000](http://localhost:3000) and click **Open workspace**. You'll be sent to sign in: choose **Continue with company account** and log in as `alice` — the first sign-in becomes the workspace owner.

For a real deployment (your own Keycloak, via Docker Compose or Helm), see [Self-hosting](/docs/self-hosting).

<Callout type="info">
  Boards and regions live in Postgres; uploaded screenshots live on a filesystem
  volume (`./data/` from source, or the mounted volume in production). Back up
  both together, including the private `release-assets/` directory used by
  recorded decisions.
</Callout>

## 2. Create a board

On `/boards`, click **New board**. Give it a name, usually a product or a quarter, e.g. `StateBoard`. The description is optional.

The development build opens the product **Overview** after creation. Add features and follow the [release workflow](/docs/release-readiness). **Release reviews** holds candidate reviews. Choose **Screens** to open the visual editor. Existing boards need no conversion.

Already have a visual board that's close to what you need? Click **Duplicate** on its card to deep-copy every screen and region into a new board, then swap only the screens that changed — faster than starting over.

Each board has an internal ID used in its workspace URLs. Public visual links use revocable tokens at `/share/{token}`; curated release links use separate tokens at `/share/releases/{token}`. Keep internal assessment URLs for workspace members and publish the public summary deliberately.

### Edit a board and move between pages

Choose **Edit board** beside the product name or on its row in the board list. Update the name and description under **Board settings**, then choose **Save changes**. **Discard changes** restores the last saved values. These actions require editing permission. Switching settings sections keeps the draft. Leaving settings closes the form, so save or discard first.

Use the header breadcrumbs to return to a parent page. The named board returns to its product overview. **Release reviews** returns from a candidate to that board's review list. On narrow screens, the header shows the immediate parent link. Product section tabs move between views within the board. Choose **History** beside **Edit board** in the product heading to see board activity.

From the visual editor, open **More board options → Edit board**. The empty editor also has an **Edit board** action. The board title is a parent link, so clicking it returns to the overview.

Browser Back and Forward restore assessment views, selected checks, categories, capabilities, and components. Search, result, and needs-attention filters stay local to each view. The board ID and existing share links stay the same after a rename.

## 3. Upload a screen

Choose **Screens** in the product workspace, then drop a screenshot onto the upload area or click to browse. Allowed formats: PNG, JPEG, WebP, GIF. Max 25 MB per file.

Upload additional screens as needed. They appear in the screen sidebar. Use its screen actions to reorder them. This order carries through to the share view and Present mode.

On narrow screens, choose **Expand screens** to open the collapsed screen rail. When header space is limited, **More board options** holds the remaining actions. These include search, visual-state filters, sharing, and Present.

<Callout type="warn">
  Don't upload anything you can't show stakeholders. Share links are public by
  design — anyone with the link can see every screen on that board, no login.
</Callout>

## 4. Mark your first region

With a screen open, **click and drag** anywhere on the image to draw a rectangle. When you release, a side panel slides in. Pick a state, give the region a label, optionally add notes.

Three states only, by design:

- **Shipped** · live, real data, fully wired up.
- **Mock** · UI is in place but data is hardcoded or fake.
- **Missing** · not built yet.

Press **Esc** at any time to discard a draft region.

## 5. Share it

On desktop, click **Share** in the editor header to copy the read-only URL. Its arrow opens **Open share view** and **Manage links**. On narrow screens, open **More board options → Copy share link**. The same menu contains **Open share view** and **Manage links**.

This visual link shows every screen and region on the board. A release review also needs features and check results; publish a [curated recorded decision](/docs/release-readiness#record-and-share-a-decision) when sharing release readiness.
