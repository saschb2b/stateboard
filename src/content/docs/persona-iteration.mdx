Six simulated personas used the actual StateBoard UI on 13 October 2026 to review **Codex-assisted StateBoard delivery**. They found the candidate and missing evidence, but encountered avoidable work locating relevant checks, interpreting local passes and reviewing decision context. The resulting refinements support those tasks. They do not establish production availability, customer demand or comprehension by actual human customers.

This case assesses StateBoard delivery operated through Codex. The Codex task and tool harness is an external component describing observed local work; its internal architecture, overall security and release readiness remain unverified. See the [usage guide](./release-readiness) and [MVP implementation contract](./release-readiness-mvp).

## Owner feedback and interface redo

The owner rejected the first refinement as bloated and lacking visual and UX focus. The simulated reviews below did not predict that response. The interface was subsequently rebuilt around one latest release, compact history, early view navigation, and expandable capability, dependency, check and decision rows. Repeated context and instruction paragraphs moved out of the main reading surface. Narrow-panel verification also exposed and fixed header overflow and cramped status columns. These changes have been exercised in the real local case; visual acceptance by the owner remains a separate judgment.

## Case and probe boundaries

The assessment pins StateBoard candidate `git:60d0a3a611c3e59f0e55675d52ee3b7198158021`, with local-development validation, a self-hosted-production target and local Postgres/Keycloak configuration without integrated evidence providers. Its reviewers span product, backend, QA, frontend, operations and release ownership.

The independent first round observed revision 13: **Needs evidence**, zero failed required checks and four evidence gaps. Eight required checks had four passing local observations and four missing claims. Six capability cards did not independently cover the two release-wide gates. A passing capability badge did not imply approval of the assessment.

Passing histories were recorded local attestations with actor, source/run reference, observation/receipt times and exact candidate/check/environment/audience/configuration. Inspecting them was not an independent test rerun. Source text and optional supporting links do not authenticate a producer; StateBoard does not fetch those links.

The personas opened and canceled forms without appending evidence, recording decisions, publishing reviews or changing access. No private raw evidence, media, credentials or share tokens appear here. Automation wall time is not a human usability measurement.

## Third round: clarity after the redesign

Three agents independently exercised simulated role perspectives on the real **Codex-assisted StateBoard delivery** case: product/customer, backend/frontend, and QA/operations/release ownership. The stored candidate was `git:1d05fa1da830d6fd76ef5525ac87c83267d400e8`, revision 20: **Needs evidence**, a held decision, zero blockers and two evidence gaps. That candidate predates the redesigned source; these probes assess the current interface, not the stored candidate's implementation.

The product probe identified the hold, outstanding restoration and human-comprehension checks, and accountable owners from the overview. Following each attention item opened the exact check and method. The public summary distinguished local validation from production availability. Remaining friction involved generic reasons, technical timestamps and scope surviving navigation into the wrong role view.

The agents' initial probes used their own browser tabs. After their browser surfaces disconnected, root performed the following post-fix retests on the actual case; these were mediated retests, not renewed independent persona sessions:

- Overview attention items distinguish **Missing evidence** from **Inconclusive**, retaining owners.
- The public review shows readable UTC dates, preserves exact timestamps, and states that the saved review does not update when evidence changes or expires.
- Opening a functional check, then switching to Operations, shows the restoration check rather than retaining the unrelated focused check.
- Screens → Judge whether this code candidate is ready → Checks preserves that capability and its two release-wide gates. Clearing the capability restores all nine checks while remaining in Checks. The real case has no linked screens; an additional interaction story covers the populated-screen handoff.
- Overview → Trace the implementation behind an outcome → View architecture selects that capability, showing six of ten components and three checks, including the two release-wide gates.
- Within that architecture slice, following the API's transactional-store dependency expands and focuses the store row and collapses the API row. The capability scope and three checks remain unchanged.

All six repository gates passed: typecheck, lint, formatting, **180 unit tests**, **122 browser stories across 42 files**, and the production build. The unit command skipped its separate database integration case; persistence was unchanged. One unsupported test-locator option was corrected after the first typecheck; the affected stories, lint, typecheck and build passed afterward. The build retains five existing dynamic-filesystem tracing warnings in screen upload/clone routes. Root observed no browser console errors. Desktop interaction and layout were checked; the browser's narrow viewport override did not apply, so this round does not establish a fresh narrow-panel result.

The implementation was saved in five scoped commits: `1843d9f` (precise evidence reasons), `5a3ec51` (public review dates), `f69b00e` (role navigation), `c3b7b96` (dependency navigation), and `a855475` (capability handoff).

This round changed no assessment records, evidence, decisions or publications. Production restoration and actual human comprehension remain unverified. Simulated role reviews and successful UI navigation cannot satisfy those claims.

## Bounded repeat workflow

1. Pin candidate, environments, audience, configuration and check revisions. A changed tuple requires a new assessment; never transfer a pass by relabeling it.
2. Give the six simulated perspectives concrete actual-UI tasks. Record observed completion/confusion/unknowns and distinguish independent from mediated navigation. Open/cancel forms for read-only inspection.
3. Separate UI defects from missing operational/customer evidence. Make scoped changes with meaningful interaction and pure-logic tests.
4. Run all six gates and relevant Postgres checks; repeat original tasks on the changed UI. Retain infrastructure limitations instead of assigning a pass.
5. Record validated outcomes, final commits and exact candidate context. Append evidence only when the observation supports that claim/revision; preserve production and human-comprehension unknowns.
6. Stop after the scoped changes pass validation and retest outcomes are recorded. Further rounds need a reason or request. A continuous scheduler, recurring monitor or future wakeup requires explicit user authorization and cannot be inferred from this finite iteration.
