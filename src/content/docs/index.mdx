**StateBoard** shows what works, what it depends on, and why a team believes a release is ready. Capabilities connect the outcomes a product must support to implementation dependencies and verification evidence. Product, frontend, backend, QA, operations, and release owners inspect the same assessment through views relevant to their work.

These docs explain how to use it.

## Why this exists

An annotated screenshot makes a visible feature easy to judge. Backend developers also need its services, API operations, events, and data dependencies; QA needs acceptance claims and results; a release owner needs the complete scope and unresolved gates.

StateBoard keeps that context connected. Capabilities can span several screens or have no UI. Evidence supports specific claims in an identified candidate, environment, audience, and configuration, and a human records the release decision.

The visual editor remains available: mark screen regions as `shipped`, `mock`, or `missing`, then share the visual board. Release assessments add verification and preserved review artifacts without changing those visual delivery labels.

## The current release

The latest published release is **2026.8.0: team-ready**. Its full feature list lives in the [changelog](/docs/changelog). Highlights:

- Manual screenshot upload, region tagging, three states (`shipped` / `mock` / `missing`)
- Read-only public share links: revocable, multiple per board
- Multi-user via Keycloak / OIDC, with `owner` / `editor` / `viewer` roles
- API keys and a built-in MCP server, so [agents can read and update boards](/docs/agents)
- Postgres-backed, multi-replica safe, append-only audit log

The **current development build** implements the release readiness workflow, including capabilities, dependencies, manual and REST evidence, six views, human decisions, retained media, and curated public reviews. This work is unreleased and is not part of `2026.8.0`. Follow the [release readiness guide](/docs/release-readiness) or explore the [example assessment](/share/demo/releases). The [roadmap](/docs/roadmap) describes the sequence and remaining backlog.
