---

StateBoard evaluates whether intended users can complete the critical capabilities in a named release candidate. Screenshots show the visual implementation; dependencies explain the wiring; evidence supports specific acceptance claims. Everyone reads the same assessment through the view relevant to their work.

**Status: RR1–RR7 ship in 2026.10.0.** The release includes migrations `0008`–`0010`, product and assessment editors, review views, evidence, decisions, retained media, public sharing, and the in-memory example. RR7 provides ordinary AI maintenance through MCP and the packaged agent skill. See the [usage guide](./release-readiness). A real team pilot and external GitHub milestone reconciliation remain follow-up work.

## MVP outcome and boundaries

Pilot one product board, one real release candidate, and roughly 5–10 critical capabilities, including one capability with no UI. A product manager, backend developer, QA specialist, and release owner should independently identify readiness, blockers, accountable owners, and the exact evidence needed to unblock the candidate.

The MVP includes capability and dependency editing, release scope, versioned acceptance checks, manual, REST, and MCP-submitted evidence, deterministic readiness, task-based review and role filters, human decisions, retained snapshots, and curated release sharing. External agents can populate and maintain capabilities, dependencies, scope, checks, and evidence from their existing engineering workflow. Existing screenshots, normalized regions, visual states, board sharing, and visual MCP tools continue to work.

Defer server-hosted discovery/LLMs, catalog/specification import engines, telemetry collection, provider SDKs, polling, test execution inside StateBoard, deployment orchestration, portfolio rollups, configurable approval workflows, and gate waivers. External coding agents may inspect source/interfaces and maintain grounded declared mappings now; that does not require an import engine or establish runtime truth. External issue and evidence links are references; StateBoard never fetches them. Use the existing local filesystem, Postgres, OIDC, MUI, REST, and API keys without a new runtime service.

## Human workflow

The interface uses **Release reviews** for assessments and **Features** for capabilities. The API, stored model, and readiness semantics retain their existing names. A feature remains an observable user or business outcome, including work without a screen.

People can complete the ordinary flow without an AI connection: define what should work, describe how to check it, record what happened, and ask an owner to review the decision. Expand a feature within a release review to create its check and record a result in context. Inherit the selected target and known owner/environment; show uncommon check settings on demand. Keep a result and observation prominent in manual entry, expose source/time details, and assign a unique human review reference automatically.

A new review can prefill environments, audience, and configuration from the latest review, with its source and current values visible for confirmation. Keep the candidate name/reference empty, show included feature selection, and preserve the first-review form's visible required fields. This reuse copies neither checks nor evidence.

Supporting systems and screen links belong beside the feature they explain. Neither architecture nor screenshots is a required setup stage. Reuse known record identities instead of asking people to recreate or relink them. Preserve all candidate, revision, scope, attribution, and access checks when simplifying forms.

## Shared product model

A **board** groups one product or product area. A **capability** describes an outcome such as exporting an invoice or completing overnight reconciliation. Capabilities are reusable within that board and may link to zero, one, or several regions. Do not convert existing rectangles into capabilities automatically or require old boards to adopt the new model.

A **component** is a lightweight workspace-owned reference to a service, API operation, event, worker/job, data store, or external dependency. Store only its identity, kind, owner, explanation, and optional internal documentation/interface link. API operations and events can be named references rather than a full schema registry.

Link capabilities to their implementing components and components to their declared dependencies. Describe the actual relation, for example `calls POST /exports`, `consumes invoice.requested`, or `requires invoice data`. Mark requirements as required or supporting context. The graph explains potential impact; only explicitly required acceptance checks determine release readiness. A component without checks displays "No verification configured."

An **assessment** evaluates one immutable candidate/context tuple:

- Candidate reference identifying an immutable artifact or pinned component-version manifest; a mutable branch name or `latest` tag is insufficient. Keep a friendly candidate label separately.
- Validation environment, such as staging, and target deployment environment, such as production.
- Intended audience and configuration reference, including relevant feature-flag/permission assumptions.

The assessment also records its included capability IDs and applicable release checks as editable scope.

Changing candidate, either environment, audience, or configuration creates a new assessment. Capability scope and checks can be edited in a live assessment with revision checks and audit. Scope exclusions and requirement changes appear explicitly in the decision review.

Pin each included capability's outcome and definition revision in the assessment. Editing the reusable capability never silently changes that assessed outcome. Show when its current definition differs; explicitly adopting the new definition updates the pinned copy, creates revisions of the affected acceptance checks, and makes their previous evidence inapplicable. Moving a check to a different subject creates a new check ID.

The implementation adds `0008_release_readiness.sql`, `0009_evidence_credential.sql`, and `0010_release_invariants.sql` after the existing `0007` migration. Keep all queries, transaction management, workspace constraints, and snake_case-to-camelCase mapping in `src/lib/db.ts`. Extend strict types and audit actions rather than changing existing region records.

| `release_decisions`       | Assessment/reviewed revision, human actor, approved/held, rationale, evaluated time, evaluator version, complete snapshot                                                  | Immutable and self-contained; approved requires calculated `ready`.                                       |

| `release_share_links`     | Revocable token, decision ID, immutable allowlisted projection and selected asset IDs                                                                                      | Separate from existing full-board share links; projection references only retained assets.                |

Each capability and check has an accountable owner label; a workspace member reference is optional. Removing a member preserves recorded team labels and historical attribution and surfaces any reassignment need. View presets do not create team membership or additional access roles.

Excluding a capability explicitly deactivates its checks in the same audited scope change, with a reason and revision increment. Re-inclusion requires a reviewed pinned definition and active required acceptance checks. Removing a component relationship cannot silently deactivate configured component or release checks; changes to those gates require their own explicit audited revision.

Archive referenced capabilities, components, and checks instead of destroying their history. Reject board deletion with a descriptive `409` when release history exists; ordinary deletion must not cascade away evidence, decisions, or retained assets. Administrative purge and retention policies are deferred. Keep existing deletion behavior for boards without release history.

Limit text lengths, JSON body size, graph size, and manifest/evidence payloads at the API boundary. Validate nested IDs against the workspace and board in the DB boundary, including region links, check subjects, dependencies, and shared assets. The singleton workspace is not a substitute for these constraints.

## Checks and evidence

Every included capability needs at least one **required functional acceptance check** expressed as an observable outcome. For example: "An authorized finance user receives a valid PDF for an existing invoice." Each check also identifies how it will be verified, its accountable owner, and the environment in which evidence is required. Additional integration, UX, data, security, and operational checks can be required or optional.

Release-level checks capture requirements that have no screen, such as migration rehearsal, permission enforcement, alert exercises, or rollback. Include the checks relevant to the team's actual release; graph membership does not generate requirements automatically.

Default check environment to the assessment's validation environment. Allow the target environment as an explicit choice when a gate actually needs deployment/configuration evidence there. A staging result may support a production release assessment only through a check that explicitly expects staging; it must not be labelled "verified in production."

Evidence results are `pass`, `fail`, or `inconclusive`. A record includes a concise claim/result summary, exact candidate/context confirmation, check definition revision, tested environment, observation time, source and run/attempt reference, actor, and optional HTTP(S) evidence URL. Record server receipt time separately. Reject malformed results, incompatible context, implausible future times, and unsafe URL schemes. API submissions use an explicit event identity for idempotency: identical retries return the original record; conflicting reuse returns `409`.

Manual entry is a human attestation, not a claim that StateBoard executed a test. Machine-submitted evidence has source and credential attribution, not a blanket guarantee of accuracy. Store result summaries and metadata locally. A URL's remote contents may change; only retained data and media form the historical evidence baseline.

Freshness is per check, measured from `observedAt`; use a positive duration with a visible default of 24 hours that the editor can change. Updating a board, correcting a label, or receiving an old result does not renew verification. New evidence supersedes the current selection without modifying or deleting earlier evidence.

## Readiness evaluation

Implement a pure evaluator in `src/lib/readiness.ts`, with an explicit clock and evaluator version. Return assessment and capability readiness, selected evidence IDs, and structured reasons suitable for every view. Calculate on read and again inside decision creation; do not store an independently editable readiness badge.

For each active check:

1. Filter evidence to the exact assessment, candidate/context, expected environment, and active check revision.
2. Select by observation time descending, then server-assigned sequence descending. Arrival order must not let an old run overwrite a newer failure. Never select a result because it passed.
3. Evaluate the selected record's result and expiry. A fresh pass satisfies the check. Missing evidence, stale passing evidence, or an inconclusive result leaves it unverified. A selected failure remains a blocker with an expiry warning if stale. A newer applicable result replaces that selection, but a stale pass cannot satisfy the current claim.
4. Preserve previous failures in history and show prior failures alongside an inconclusive latest result. Readiness follows the selected result; prior failures are context, not a separate sticky state. Never fall back to an older passing result.

| Condition                                                                                                   | Calculated readiness                          |
| ----------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Any required check's applicable selected result is `fail`                                                   | `blocked`; also show all other evidence gaps. |
| No required failures, but any required check is missing, inconclusive, stale, or has no applicable evidence | `needs_evidence`.                             |
| Empty capability scope, or an included capability lacks a required functional acceptance check              | `needs_evidence`.                             |
| Every required claim has a fresh matching pass                                                              | `ready` for the assessed candidate and scope. |

Optional failures and gaps remain visible as warnings. Required component/release checks contribute only when configured explicitly. Readiness is not a weighted percentage, rectangle count, ticket count, or inference from component uptime. Visual `shipped` / `mock` / `missing` states stay independent.

No waiver or "ready with exceptions" path ships in the MVP. An owner can approve only calculated `ready`, or record a hold with a rationale at any readiness. Readiness describes the assessed evidence; approval records the human judgment and does not deploy anything.

## Views and navigation

Add an assessment workspace under `/boards/[id]/releases/[releaseId]`. Keep candidate, validation/target environments, audience, overall readiness, and evidence-gap counts visible while switching views. Preserve the selected view in the URL so a colleague can open the same context.

| Destination                      | Primary question                                   | Content and useful actions                                                                                         |
| -------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Overview                         | Can users achieve the intended outcomes?           | Conclusion, findings, included features, and contextual checks/results.                                            |
| Checks                           | Which claims have applicable observations?         | All checks, result history, focused claims, and category/attention filters.                                        |
| Decision                         | What exactly am I approving or holding?            | Full scope, required failures/gaps, optional warnings, retained artifacts, reviewer, and rationale.                |
| Screens, supporting context      | Which visible interactions support a feature?      | Existing screens/regions, feature links, expected behavior, and matching verification.                             |
| Architecture, supporting context | What implements this outcome and what is affected? | Relevant systems and relationships; select a feature/component to reveal its checks and release-wide requirements. |

Operational, security, and data concerns filter the same check records. Preserve legacy role-view URLs, including Operations, rather than breaking links. A category without checks remains unassessed. Board navigation uses Overview, Release reviews, and Features, with Architecture combining optional components and connections.

Each destination presents the same server-loaded assessment. A product view is not automatically public. Start architecture navigation with the selected feature and immediate relationships; expand explicitly, deduplicate shared components, and use a visited set and bounded traversal. Use a grouped component list and accessible relationship table. No free-form diagram editor is needed.

## Authorization and public sharing

Retain workspace `viewer`, `editor`, and `owner` permissions. Viewers read internal assessments. Editors and appropriately capped API keys maintain definitions and append evidence. A current owner with a browser session records decisions and creates/revokes public release links. Finalization and publication endpoints reject bearer-authenticated requests even if the key is owner-scoped.

Add a session-only API guard: the existing `requireApiMember("owner")` accepts API keys and therefore cannot enforce human decisions. Revalidate and lock current membership inside decision and publication transactions so concurrent demotion cannot authorize a write. Enforce origin checks on new cookie-authenticated mutations. Add credential/source metadata for evidence attribution without exposing tokens or hashes. Every mutation writes audit in the same transaction as its data changes.

Public release links refer to a recorded decision, not the mutable live assessment. Construct an immutable allowlisted projection on the server: candidate label, reviewed date, target environment/audience summary, outcome summaries, readiness and evidence-gap summary, approved public explanations, and explicitly selected safe screenshot copies. The internal snapshot remains authenticated.

Exclude raw architecture, internal evidence URLs, source/run identifiers, member identities/emails, internal notes, configuration secrets, and private asset paths. Select public-safe outcome summaries and media explicitly before publishing. Verify the exclusion in server JSON, HTML, metadata, and asset responses, not just in visible components. Existing labelled board links still show the same full board and retain their current semantics.

New confidential images and retained decision copies use a private directory resolved through `src/lib/paths.ts`. Serve them through authenticated assessment/decision asset routes, or a release token that authorizes that exact projected asset. Use `no-store` and the existing filename/MIME validation patterns. Token revocation blocks subsequent page, API, and asset reads; it cannot retract previously downloaded bytes.

Current board images are already available through public `/api/uploads/[filename]` with long-lived caching. Copying them into private snapshot storage does not undo that exposure. Treat legacy visual anchors as potentially public, show this when selecting them, and do not place confidential architecture or new evidence uploads in that directory. A broader migration of existing board image access is a separate follow-up.

## Recorded decisions and media retention

The owner submits the assessment revision shown in the review. In one DB transaction, lock the assessment, compare that revision, re-evaluate at server time, enforce the decision condition, and write the decision, snapshot, and audit. All scope, definition, evidence, and relevant mapping mutations must participate in the same revision/locking contract. A concurrent edit or evidence arrival causes `409` and requires a refreshed review. Evidence expiry is checked even when the revision has not changed.

Make revision propagation explicit: edits to shared component metadata/dependencies, mappings, owners, or linked visual data used by a live review bump every affected assessment revision. The MVP serializes writes with a shared workspace → board/source → assessment lock order, then locks membership and credentials before authorization-sensitive writes. Shared component mutations lock affected boards and assessments in deterministic ID order inside that workspace boundary. Evidence, decisions, media replacement/deletion, and member changes follow compatible ordering. This deliberately coarse workspace lock favors consistent reviews over maximum write concurrency in the singleton deployment. Pinned outcome changes follow the explicit definition-adoption rule above. Reads use a consistent transaction snapshot so they cannot combine rows from different revisions.

Snapshot the candidate/context, included capabilities and owners, scope explanations, check definitions and revisions, declared dependency slice, selected evidence and provenance, readiness reasons, evaluation time/version, and normalized visual annotations. Retain any media the owner includes as independent immutable bytes with digests, rather than live screen filenames.

Stage media copies before recording. Coordinate screen replacement/deletion with the same source-row/asset locks; these handlers currently remove old files. Revalidate source identity/digest and the assessment revision before committing. Remove staged files on failure and provide a local cleanup command for abandoned staging files. A successful decision must never reference a partial or absent copy.

Replacing/deleting a live screen, editing a capability, receiving new evidence, or removing a member must not rewrite the snapshot. Keep the live assessment editable; later decisions append another snapshot. Historical views say "As assessed at [time]" and show the recorded freshness limit. If live evidence has expired or changed, show that distinction rather than presenting an old approval as current verification.

## AI maintenance completion

MCP and the packaged StateBoard skill are part of the MVP rather than a later integration. An editor agent should complete a bounded setup/update cycle without asking a person to enter each field: inspect the existing product and repository, reconcile meaningful outcomes and declared implementation relationships, define the actual candidate/context, maintain required acceptance checks, run authorized verification externally, submit observations, and return readiness plus unresolved claims for review.

Expose `get_product`, `get_release`, `get_release_readiness`, and `get_check_history`; capability/component editing and archive tools; capability/component and region/capability links; dependency creation/removal; assessment creation and scope changes; check creation/revision/archive; and evidence submission. Return structured results with current context/revision/readiness so agents can continue without guessing. Use consistent, machine-readable error codes for validation, authorization, missing resources, and conflicts. The complete tool/argument contract lives in [Agents & API](./agents) and the server's discoverable schemas.

Agents reuse existing identities and preserve definitions/history. A source-derived relationship includes its basis and remains declared context. Actual test observations are attributed to their producing credential, exact candidate, context, and check revision. A changed candidate requires another assessment; an old passing run cannot be copied as fresh evidence. No observation means missing evidence, while an attempted but inconclusive verification remains inconclusive. Simulated roles cannot provide independent human review. Required gates cannot be quietly removed to obtain readiness.

On subsequent authorized changes, agents update the affected slice; CI can push the same result format on completed runs. StateBoard does not schedule or execute that work and gains no outbound network calls. Humans supply materially missing release intent and remain responsible for release decisions and publication. Routine repository-grounded entry does not need human confirmation for every field.

## Verification and acceptance cases

Pure tests should cover the evaluator and projection boundaries, not reproduce component markup. Add DB/API integration coverage where ownership, transactions, idempotency, and asset lifecycles cannot be verified by pure functions. Verify that reusable outcome changes leave an assessment's pinned outcome intact, explicit definition adoption invalidates affected evidence, and moving a check cannot transfer its old pass to another subject. Include concurrent owner demotion and idempotent/conflicting evidence retries.

| Case                                                                        | Expected result                                                                                                       |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Empty assessment or included capability with no required functional check   | `needs_evidence`; approval rejected.                                                                                  |
| Passing UI rendering/contract check but failing required user outcome       | `blocked`; supporting passes remain inspectable.                                                                      |
| Required failure plus another missing check                                 | `blocked`, with the missing claim also visible.                                                                       |
| Wrong candidate, environment, audience/configuration, or check revision     | Cannot satisfy the current check; mismatch is explained.                                                              |
| Expired passing result; check edited; late result from an older run         | Cannot restore ready; prior results remain in history.                                                                |
| Stale failure, inconclusive latest run, or optional failure                 | Stale failure remains blocked; inconclusive cannot establish ready; optional failure is a warning.                    |
| Shared components and dependency cycles                                     | Bounded traversal and deduplication; graph edges alone do not create gates.                                           |
| Viewer writes; foreign workspace/board IDs; removed/demoted/expired keys    | Denied consistently, including nested links and assets.                                                               |
| Owner-scoped API key records a decision or publishes a release link         | Denied; live owner browser session required.                                                                          |
| Evidence/scope changes during review, or expiry before submission           | Revision conflict or refreshed non-ready calculation prevents approval.                                               |
| Live screen replaced/deleted or board deleted after decision                | Retained media/text survive; board deletion with history returns a descriptive conflict.                              |
| Public JSON/HTML/metadata/media inspected; token revoked                    | No private fields or unselected assets; revoked token denies fresh reads.                                             |
| Existing board editor/share/REST/MCP and static demo                        | Existing visual semantics and working routes remain intact.                                                           |
| MCP creates product context, assessment, checks, and evidence               | Same stored records, attribution, revision advancement, and readiness as REST; no parallel AI model.                  |
| MCP editor attempts invalid nested IDs, stale edits, or conflicting retries | Same authorization, ownership, definition, and event identity guards as REST; structured errors guide reconciliation. |
| Agent reconciles a changed project with existing product records            | Reuses IDs and preserves history; source-derived wiring remains declared context and unexecuted claims remain gaps.   |
| Read-only/owner-scoped MCP credentials and missing verification             | Viewer mutations fail; no key can decide or publish; incomplete evidence never produces a ready result.               |

Before completing each implementation slice, run the six existing gates: `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm test:stories`, and `pnpm build`. For UI slices, exercise the full application with Postgres/OIDC and use Storybook interaction tests. For final acceptance, inspect both the authenticated release workflow and a public projection in a browser and verify the Pages export in a disposable environment.

## Pilot and follow-up decisions

Extend `getDemoBoard()` through a separate in-memory release fixture, including passing, failed, missing, stale, and wrong-context evidence, a nonvisual capability, shared dependencies, and a recorded decision. No fixture is seeded into the user database. Link empty capability, assessment, evidence, and role views to that example.

For the real-release pilot, have product, backend, QA, frontend, operations, and a release owner independently answer whether the candidate is ready, which claims block it, who owns the resolution, and what evidence is needed. Use two minutes to find the answers as an initial usability target, not an established benchmark. Track preparation time, maintenance per review, disagreements, and false-ready conclusions as well as comprehension.

After the pilot, prioritize actual recurring evidence sources and import needs. Reconcile GitHub milestones/issues with the adopted roadmap, keep marketing and agent guidance aligned with the implemented surface, and consider catalog imports, configurable exception policy, private legacy image migration, or broader impact views only against demonstrated needs. This documentation change does not create or relabel GitHub milestones.

## Research foundations

These mechanisms inform the design; they do not establish market demand for the combined StateBoard product:

- [Backstage software catalog](https://backstage.io/docs/features/software-catalog/) and [Cortex relationship graph](https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/relationship-graph): ownership, relationships, and focused navigation.
- [C4 diagrams](https://c4model.com/diagrams) and [Cucumber BDD](https://cucumber.io/docs/bdd/): audience-specific architecture views and shared acceptance language.
- [Pact testing boundaries](https://docs.pact.io/getting_started/what_is_pact_good_for): a contract result supports compatibility claims, not every business outcome or side effect.
- [Allure TestOps overview](https://docs.qameta.io/getting-started/overview/) and [OpsLevel checks](https://docs.opslevel.com/docs/checks-and-filters): scoped manual/automated verification and expiring checks.
- [Unleash feature flags](https://docs.getunleash.io/concepts/feature-flags) and [Google SRE user-centric objectives](https://sre.google/workbook/implementing-slos/): environment/audience context and critical user journeys.
